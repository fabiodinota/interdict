## Task 1: Rego template engine, policy CRUD hooks, and policy list with version history

<task>
<title>Build Rego template engine, TanStack Query policy hooks, and policy list with expandable version history</title>
<context>
**Policy templates** generate valid Rego source code from structured form inputs. Each template is a TypeScript object that defines:
- Category (vendor_control, content_inspection, rate_limiting, custom)
- Name and description
- Parameters (typed form fields: text, select, toggle, number, multi-select)
- A `generateRego()` function that produces valid Rego from parameter values

**Locked template set (5-7 templates):**
1. Block Vendor -- block/allow requests to a specific vendor
2. PII Detection/Redact -- detect and redact personally identifiable information
3. Rate Limit by Department -- limit request volume per department per time window
4. Content Length Limit -- block requests/responses exceeding a token count
5. Allowed Model Versions -- restrict usage to specific model versions
6. Jurisdiction Restrict -- block requests based on regulatory jurisdiction

**Policy list** uses an expandable row pattern: each row shows the policy name, status (active/inactive toggle), compilation status badge, and creation date. Clicking a row expands it to show the full version history with:
- Version number and timestamp
- Change description
- A "diff view" comparing the current version's Rego source with the selected version
- A "Restore" button to restore a previous version (calls POST /policies/:id/restore/:versionId)

**API endpoints (via BFF proxy):**
- GET /api/proxy/policies -- list policies (cursor-paginated)
- POST /api/proxy/policies -- create policy (sends { name, description, rego_source, entrypoint })
- PUT /api/proxy/policies/:id -- update policy (creates new version)
- DELETE /api/proxy/policies/:id -- soft-delete
- GET /api/proxy/policies/:id/versions -- version history
- POST /api/proxy/policies/:id/restore/:versionId -- restore version
- GET /api/proxy/policies/:id/compilation-status -- poll compilation status

**Important:** The API pre-validates Rego syntax on create/update. If the Rego is invalid, the API returns 400 with "Invalid Rego syntax" and error details. The wizard preview step should submit and handle this error gracefully.
</context>

   export type ParameterType = "text" | "select" | "toggle" | "number" | "multi-select";

   export interface TemplateParameter {
     key: string;
     label: string;
     type: ParameterType;
     description?: string;

     placeholder?: string;
   }

2. Create `dashboard/src/lib/rego-templates.ts` -- the 6 policy templates:
   - Each template defines its `parameters` array and a `generateRego()` function
   - The Rego output must follow the Interdict policy package structure: `package interdict.policy` with `import rego.v1`
   - All generated Rego produces a `verdict` object with `{ "action": "allow"|"block"|"redact" }`
   - String values in Rego must be properly escaped (no template injection)
   - Export a `POLICY_TEMPLATES` array and a `getTemplatesByCategory()` grouping function
   - Export a `POLICY_CATEGORIES` array: `[{ id: "vendor_control", name: "Vendor Control", icon: "Building2", description: "..." }, ...]`

   Template details:
   a. **Block Vendor**: params = vendor_name (select, populated dynamically from vendors API), action (select: block/allow). Generates Rego that matches `input.request.vendor`.
   b. **PII Detection/Redact**: params = pii_types (multi-select: email, phone, ssn, credit_card, address), action (select: redact/block), sensitivity (select: low/medium/high). Generates Rego that checks content inspection results.
   c. **Rate Limit by Department**: params = department (select), max_requests (number), time_window_minutes (number), action (select: block/throttle). Generates Rego using rate limit counters.
   d. **Content Length Limit**: params = max_tokens (number), direction (select: request/response/both), action (select: block/warn). Generates Rego checking `input.request.token_count` or `input.response.token_count`.
   e. **Allowed Model Versions**: params = vendor (select), allowed_models (multi-select), action (select: block/allow). Generates Rego matching `input.request.model` against the allowlist.
   f. **Jurisdiction Restrict**: params = blocked_jurisdictions (multi-select: list of jurisdiction codes), action (select: block). Generates Rego checking jurisdiction metadata.

## Task 2: Policy Builder wizard (5-step + raw editor)

<task>
<title>Build the Policy Builder multi-step wizard with category picker, template picker, parameter form, visual rule editor, Rego preview, and raw editor toggle</title>
<context>
The Policy Builder is a 5-step wizard:
1. **Category Picker** -- Pick from 4 categories (vendor_control, content_inspection, rate_limiting, custom)
2. **Template Picker** -- Pick a template within the selected category
3. **Parameter Form** -- Fill in template-specific form fields
4. **Visual Rule Editor** (optional) -- Add/modify conditions using simple rows: [Field] [Operator] [Value] with AND/OR connectors
5. **Rego Preview** -- See the generated Rego source, submit to create the policy

At any step, the user can toggle to a **Raw Rego Editor** where they write Rego manually. Toggling back to the wizard resets the wizard state (the raw editor is an escape hatch, not bidirectional).

The wizard submits by calling POST /api/proxy/policies with `{ name, description, rego_source, entrypoint }`. On success:
- Navigate to the policies list
- Show a toast notification
- Start compilation status polling on the new policy

**Step 4 (Visual Rule Editor)** uses simple condition rows like email filter rules:
```
[Field dropdown] [Operator dropdown] [Value input]  [AND/OR toggle]  [+ / - buttons]
```
Fields available: input.request.vendor, input.request.model, input.request.token_count, input.response.token_count, input.request.department, etc.
Operators: ==, !=, contains, not_contains, >, <, >=, <=

These conditions are appended to the template-generated Rego as additional `if` conditions.

**For editing existing policies:** The wizard can be opened with a `?edit=<policyId>` query parameter. In edit mode, it loads the existing policy's Rego source into the raw editor (since we can't reverse-engineer template params from Rego). The user can modify the Rego and submit as an update (PUT instead of POST).
</context>
