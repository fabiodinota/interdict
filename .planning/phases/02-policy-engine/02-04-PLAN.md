    **1. Add `PolicyPipeline` to `crates/kernel/src/policy/mod.rs`:**

    `PolicyPipeline` is the central orchestrator that the proxy calls for every intercepted request:

    ```rust
    pub struct PolicyPipeline {
        regorus_pool: Arc<RegorusPool>,
        allowlist_policy: Arc<VendorAllowlistPolicy>,
        classifier: Arc<Classifier>,
        background_l2: Option<BackgroundL2>,
        review_queue: Arc<ReviewQueue>,
        redaction_engine: Arc<RedactionEngine>,
        wasm_engine: Arc<WasmEngine>,
        policies: Vec<PolicyConfig>,
    }
    ```

    `PolicyPipeline::new(...)` — takes all components, constructed at startup in main.rs.

    `PolicyPipeline::evaluate(&self, ctx: &RequestContext) -> Result<PipelineResult>`:

    The core 3-layer flow per CONTEXT.md locked decisions:

    **Step 1: Vendor allowlist check (always first in L1)**
    - Call `allowlist_policy.evaluate(ctx)` → if Block, add to verdicts but DO NOT short-circuit (all policies must be evaluated per locked decision)

    **Step 2: Layer 1 — Evaluate all matching Rego policies**
    - For each enabled policy in `self.policies`:
      - Build input JSON from RequestContext (vendor, method, path, content, direction)
      - Call `regorus_pool.evaluate(input_json, rule)` via spawn_blocking
      - If evaluation succeeds → parse into PolicyVerdict, add to verdicts
      - If evaluation fails → apply policy's fail_mode: FailClosed → add Block verdict, FailOpen → add Allow verdict. Log the error. Per locked decision: "Layer errors use the policy's fail-closed/fail-open setting"
    - **CRITICAL: Do NOT short-circuit.** Even if one policy returns Block, evaluate ALL remaining policies. This is required for complete audit trail per locked decision

    **Step 3: Merge L1 verdicts**
    - Call `MergedVerdict::merge(all_l1_verdicts)`
    - If merged.final_action is Block or Redact (explicit verdict):
      - Enforce the verdict immediately
      - If any policy has `background_l2: true`, dispatch to `background_l2.submit()` for analytics enrichment (fire-and-forget, per locked decision)
      - Return PipelineResult with the merged verdict, no L2 foreground result
    - If merged.final_action is Allow AND all verdicts are explicit allows (not "no match"):
      - Same as above — enforce Allow, optional background L2
    - If ANY Rego policy returned "no match" (neither allow/block/redact):
      - Escalate to Layer 2

    **Step 4: Layer 2 — NLP classification (foreground)**
    - Call `classifier.classify(features)` where features are extracted from RequestContext
    - Feature extraction: for now, a simple placeholder (actual feature engineering depends on the model). Create a `extract_features(ctx: &RequestContext) -> Vec<f32>` function that returns a fixed-size feature vector. For stub: return vec of zeros
    - If classification label is "uncertain" (the dedicated output class per locked decision):
      - Escalate to Layer 3
    - If classification label is "block", "redact", or "allow":
      - Create PolicyVerdict from L2 result, add to verdicts, re-merge, enforce

    **Step 5: Layer 3 — Human review (connection hold)**
    - Build VerdictTrace with L1 results, L2 classification, request context
    - Call `review_queue.escalate(request_id, &trace, content_hash, fail_mode)`
    - Returns VerdictAction (from human decision or fail-mode timeout)
    - Create final PolicyVerdict from L3 result

    **Step 6: Build PipelineResult**
    - `PipelineResult` struct: `{ merged_verdict: MergedVerdict, trace: VerdictTrace, redaction_result: Option<RedactionResult> }`
    - If final action is Redact, apply `redaction_engine.apply(content)` to produce redacted content
    - Compute SHA-256 hash of original content (this happens inside RedactionEngine per Plan 02)

    **2. Integrate pipeline into `crates/kernel/src/proxy/connect.rs`:**

    The CONNECT tunnel handler currently does: accept CONNECT → upgrade → TLS intercept → relay bytes.

    Phase 2 integration point: After TLS is terminated from the client and before relaying to upstream, the proxy can inspect the first request. However, the current Phase 1 design uses raw byte relay (`tokio::io::copy_bidirectional`), not HTTP-level inspection.

    **Pragmatic approach for Phase 2:**
    - Add `Arc<PolicyPipeline>` to `ProxyService` constructor
    - In `handle_connect`, before starting the relay, create a `RequestContext` with vendor, method (CONNECT), path info available from the CONNECT URI
    - Call `pipeline.evaluate(&ctx)` with the available metadata
    - If verdict is Block → don't establish the tunnel, return 403 (configurable per block_response_detail)
    - If verdict is Allow → proceed with relay as before
    - If verdict is Redact → proceed with relay (content-level redaction happens in Phase 3 when we have the sliding window buffer for actual content inspection)
    - **Note:** Full content-level inspection (reading HTTP bodies through the tunnel) requires Phase 3's sliding window. Phase 2 evaluates policies based on request METADATA (vendor, path, method) not body content. This is the correct boundary per the phase scope
