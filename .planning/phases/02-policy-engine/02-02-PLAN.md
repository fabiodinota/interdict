Build Layer 1 allowlist-as-policy, Layer 2 NLP classifier, and the content redaction engine. The vendor allowlist migrates from standalone middleware to a policy verdict in the Layer 1 pipeline. Purpose: These are the evaluation and enforcement primitives that the pipeline orchestrator (Plan 04) composes into the full 3-layer flow. Each can be tested in isolation.

    **1. Create `crates/kernel/src/policy/layer1/allowlist.rs`:**
    Refactor the vendor allowlist from Phase 1's standalone middleware into a Layer 1 policy that returns a PolicyVerdict. Per KERN-11 and the explicit success criterion: "vendor allowlist check integrates with the policy pipeline so that vendor blocking is a policy verdict, not a separate code path."

    - `VendorAllowlistPolicy` struct wrapping the existing `VendorAllowlist` from middleware::allowlist (reuse the domain HashSet, don't duplicate)
    - `VendorAllowlistPolicy::evaluate(&self, ctx: &RequestContext) -> PolicyVerdict`:
      - If `ctx.vendor` is in the allowed set → return `PolicyVerdict { policy_id: "builtin:vendor_allowlist", action: Allow, redactions: vec![], reason: None }`
      - If NOT in allowed set → return `PolicyVerdict { policy_id: "builtin:vendor_allowlist", action: Block, redactions: vec![], reason: Some("Vendor not on approved allowlist") }`
    - The existing `AllowlistLayer` middleware in `middleware/allowlist.rs` should be updated to delegate to this new policy function internally, OR kept as a thin fast-path for the CONNECT handler (since vendor check happens before TLS interception). Decision: Keep the middleware as a fast-path that runs BEFORE the tunnel is established (avoiding the cost of TLS termination for blocked vendors), but the policy pipeline ALSO has the allowlist check so that the verdict appears in the audit trail. Add a comment in both files explaining this dual-check design.
    - Write unit tests:
      - `test_allowlist_policy_allows_approved_vendor` — verify Allow verdict for listed vendor
      - `test_allowlist_policy_blocks_unapproved_vendor` — verify Block verdict with reason
      - `test_allowlist_policy_id_is_builtin` — verify policy_id starts with "builtin:"

    **2. Create `crates/kernel/src/policy/redaction.rs`:**
    Implement the content redaction engine per locked decisions:
    - `RedactionEngine` struct holding a list of `RedactionRule` patterns
    - `RedactionRule` struct: `{ category: String, pattern: regex::Regex }` — NOTE: regex is not yet a dependency; use the regex support built into Regorus OR add `regex` crate. Since redaction needs standalone regex matching (not inside Rego), add `regex = "1"` to Cargo.toml
    - `RedactionEngine::apply(&self, content: &str) -> RedactionResult`:
      - First compute `sha2::Sha256` hash of the original content (before any modification). This is the "SHA-256 hash always stored" per locked decision
      - Apply each rule: find all matches, replace with `[REDACTED:{CATEGORY}]` (e.g., `[REDACTED:SSN]`, `[REDACTED:EMAIL]`)
      - Return `RedactionResult { original_hash: String, redacted_content: String, redactions: Vec<Redaction> }` where each Redaction records the category, matched text, and replacement
    - `RedactionEngine::from_rules(rules: Vec<RedactionRule>) -> Self`
    - `RedactionEngine::empty() -> Self` — no rules, returns content unchanged (still computes hash)
    - Write unit tests:
      - `test_redact_ssn_pattern` — content with "123-45-6789" → `[REDACTED:SSN]`
      - `test_redact_email_pattern` — content with "user@example.com" → `[REDACTED:EMAIL]`
      - `test_redact_multiple_matches` — content with SSN and email → both redacted
      - `test_redact_preserves_non_matching_content` — text without patterns unchanged
      - `test_redact_computes_sha256_of_original` — verify hash matches SHA-256 of original input
      - `test_redact_empty_engine_returns_content_unchanged` — no rules, content passes through

    **2. Create `crates/kernel/src/policy/layer2/classifier.rs`:**
    Implement the tract-onnx classifier per Research Pattern 5 and the tract code example:
    - `Classifier` struct wrapping `Arc<SimplePlan<...>>` (the tract model plan) and `Vec<String>` labels
    - `Classifier::load(model_path: &str, labels: Vec<String>) -> Result<Self>`:
      - Load ONNX model: `tract_onnx::onnx().model_for_path(model_path)?.into_optimized()?.into_runnable()?`
      - Wrap in Arc for thread-safe sharing
      - Store labels (must include "uncertain" class per locked decision)
      - This is the expensive path — call ONCE at startup, never per-request (Pitfall 4)
    - `Classifier::classify(&self, features: &[f32]) -> Result<ClassificationResult>`:
      - Build input tensor from features
      - Run `self.model.run(tvec!(input.into()))?`
      - Extract output scores, find max, return ClassificationResult with label, confidence, all_scores
      - The ClassificationResult type comes from verdict.rs (defined in Plan 01)
    - `Classifier::stub(labels: Vec<String>, default_label: String) -> Self`:
      - Create a stub classifier that always returns the default_label with 1.0 confidence
      - Used for testing and when no ONNX model is configured (l2_model_path is None)
      - This is critical because no real model exists yet — Phase 2 designs the interface to be model-agnostic per Research Open Question 2
    - `BackgroundL2` struct per Research Pattern 5:
      - Uses `crossbeam_channel::bounded` (KERN-13 compliant) with configurable queue depth
      - Spawns worker OS threads (not tokio tasks — classifier is sync/CPU-bound)
      - `BackgroundL2::new(classifier: Arc<Classifier>, workers: usize, queue_depth: usize) -> Self`
      - `BackgroundL2::submit(&self, item: L2WorkItem)` — non-blocking try_send; if queue full, log warning and drop (background is best-effort per research pattern)
      - `L2WorkItem` struct: `{ request_id: uuid::Uuid, input_features: Vec<f32>, result_tx: Option<crossbeam_channel::Sender<ClassificationResult>> }` — result_tx is optional; if None, result is just logged
    - Write unit tests:
      - `test_stub_classifier_returns_default_label` — stub with "allow" label returns "allow"
      - `test_stub_classifier_includes_uncertain_class` — verify labels include "uncertain"
      - `test_background_l2_submit_and_receive` — submit work item with result_tx, receive classification
      - `test_background_l2_drops_when_queue_full` — fill queue, verify submit doesn't block/panic
      - Do NOT test `Classifier::load` with a real ONNX model (no model file exists yet). The stub interface proves the API contract
