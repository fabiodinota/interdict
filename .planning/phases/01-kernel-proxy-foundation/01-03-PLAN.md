  <action>
    Create a comprehensive integration test suite that validates the proxy end-to-end using wiremock mock backends.

    **crates/kernel/tests/integration/helpers.rs -- Test infrastructure:**

    **`TestProxy` struct:**
    - Manages a proxy instance running on a random available port (bind to 127.0.0.1:0)
    - Generates a test CA cert+key pair programmatically (using rcgen, no file dependency)
    - Creates a temporary config with the test CA and a configurable allowlist
    - Spawns the proxy server in a background tokio task
    - Provides `proxy_addr()` for test clients to connect to
    - Implements `Drop` (or an async shutdown method) to clean up the proxy on test completion

    **`TestProxy::new(allowlist: Vec<String>) -> Self`:**
    - Generate CA cert+key with rcgen
    - Write to temp files (tempfile crate or std::env::temp_dir)
    - Build Config programmatically with the test CA paths and provided allowlist
    - Start the proxy server on a random port
    - Wait for the server to be ready (poll with short TCP connect attempts)

    **`TestProxy::client(&self) -> reqwest::Client` or similar:**
    - Return an HTTP client configured with HTTP_PROXY pointing to the test proxy
    - Configure the client to trust the test CA certificate
    - Alternatively, use raw hyper client with CONNECT for more control

    **`mock_vendor(responses: Vec<ResponseTemplate>) -> MockServer`:**
    - Helper to create a wiremock MockServer simulating an AI vendor
    - Returns the MockServer whose address can be added to the proxy allowlist

    **crates/kernel/tests/integration/connect_tunnel.rs:**

    **`test_connect_tunnel_basic`:**
    - Start TestProxy with mock vendor on allowlist
    - Start wiremock MockServer returning a simple 200 JSON response
    - Send HTTPS request through the proxy to the mock vendor
    - Assert: response is 200, body matches expected JSON
    - This proves: CONNECT handshake, TLS interception, upstream TLS, byte relay all work

    **`test_connect_tunnel_preserves_headers`:**
    - Send request with custom headers (Authorization, Content-Type)
    - Assert: mock vendor receives all headers intact
    - This proves: header relay is transparent

    **`test_connect_tunnel_large_response`:**
    - Mock vendor returns 1MB response body
    - Assert: client receives full body, content matches
    - This proves: streaming works for large payloads

    **`test_connect_non_connect_rejected`:**
    - Send a direct GET request (not CONNECT) to the proxy
    - Assert: 400 Bad Request response
    - This proves: only CONNECT is accepted (per CONTEXT.md)

    **crates/kernel/tests/integration/allowlist.rs:**

    **`test_allowed_vendor_passes`:**
    - Start proxy with ["mock-vendor.test"] in allowlist
    - Mock vendor returns 200
    - Send request to mock-vendor.test through proxy
    - Assert: 200 response received

    **`test_blocked_vendor_gets_403`:**
    - Start proxy with ["allowed-vendor.test"] in allowlist
    - Send request to "blocked-vendor.test" through proxy
    - Assert: 403 Forbidden response
    - Assert: response body is JSON with `"error": "vendor_blocked"` and `"vendor": "blocked-vendor.test"`
    - This validates the exact JSON error structure from CONTEXT.md

    **`test_empty_allowlist_blocks_everything`:**
    - Start proxy with empty allowlist
    - Send request to any vendor
    - Assert: 403 Forbidden (deny-by-default)

    **`test_allowlist_exact_match_only`:**
    - Start proxy with ["api.openai.com"]
    - Send request to "openai.com" (no "api." prefix)
    - Assert: 403 Forbidden (exact domain match, not substring)

    **crates/kernel/tests/integration/streaming.rs:**

    **`test_sse_streaming_incremental_delivery`:**
    - Mock vendor returns SSE-style response: Content-Type `text/event-stream`, body sent as multiple chunks with delays (e.g., 5 chunks of "data: token_N\n\n" with 50ms between each)
    - Client reads response body incrementally (not .text().await which buffers)
    - Assert: first chunk arrives within 100ms of request (not after all chunks sent)
    - Assert: all 5 chunks received in order
    - This is THE critical test for KERN-02 (SSE streaming) and research Pitfall 1 (no buffering)

    **`test_large_streaming_response`:**
    - Mock vendor sends 10,000 SSE events
    - Assert: all events received, memory does not spike (if measurable)
    - This validates streaming works at scale without buffering

    **`test_grpc_style_http2_relay`:**
    - Mock vendor speaks HTTP/2 (wiremock supports this)
    - Send HTTP/2 request through proxy
    - Assert: response received correctly
    - This validates gRPC-style HTTP/2 frame relay (KERN-03 -- gRPC is HTTP/2 DATA frames)

    **Implementation note on wiremock and CONNECT proxy testing:**
    - wiremock creates a mock HTTP server on localhost. For CONNECT proxy testing, the test client must:
      1. Connect to the proxy
      2. Send CONNECT to the mock vendor's host:port
      3. Upgrade to TLS (using the test CA)
      4. Send the actual HTTP request through the tunnel
    - This requires either a CONNECT-aware HTTP client library or manual implementation using hyper's low-level API.
    - Consider using `reqwest` with proxy configuration for simplicity, or build a small test helper that does the CONNECT + TLS dance manually.
    - The mock vendor may run on localhost:random_port. The allowlist needs to include "127.0.0.1" or "localhost" for tests. Alternatively, the test helper can inject the mock vendor's address into the allowlist.

    **Test organization:**
    - All tests use `#[tokio::test]`
    - Each test creates its own TestProxy instance (test isolation)
    - Tests clean up on completion (TestProxy Drop)
    - Tests should complete within 10 seconds each (generous for CI)

    Create integration tests for the connection pool under concurrent load and backpressure behavior, plus criterion benchmarks measuring the three performance requirements.

    **crates/kernel/tests/integration/connection_pool.rs:**

    **`test_pool_creates_multiple_connections`:**
    - Start proxy with max_connections_per_vendor=2, max_streams_per_connection=5
    - Send 10+ concurrent requests to the same mock vendor (spawning 10+ tokio tasks)
    - Assert: the proxy opens 2 connections to the vendor (observable via mock vendor connection count, or by checking pool stats)
    - This validates KERN-12 (multiple HTTP/2 connections per vendor)

    **`test_pool_reuses_connections`:**
    - Send 5 sequential requests to the same vendor
    - Assert: all requests succeed and only 1 connection was created (under stream limit)

    **`test_pool_distributes_load`:**
    - Configure small stream limits (max_streams=2, max_conns=4)
    - Send 8 concurrent requests
    - Assert: connections are opened as needed, streams distributed across connections

    **`test_concurrent_200_streams`:**
    - Configure max_conns=4, max_streams=100
    - Send 200+ concurrent requests
    - Assert: all succeed without stream exhaustion errors
    - This validates Phase 1 success criterion #4: "sustaining 200+ concurrent streams"

    **crates/kernel/tests/integration/backpressure.rs:**

    **`test_503_when_queue_full`:**
    - Start proxy with max_request_queue=2 (very small)
    - Mock vendor introduces 500ms delay per response
    - Send 10+ concurrent requests rapidly
    - Assert: some requests receive 503 Service Unavailable with structured JSON body
    - Assert: JSON body contains `"error": "service_overloaded"` and `Retry-After` header
    - This validates bounded queue backpressure (KERN-13 principle)

    **`test_recovery_after_backpressure`:**
    - Trigger 503 backpressure
    - Wait for queued requests to complete
    - Send new request
    - Assert: new request succeeds (proxy recovers)

    **crates/kernel/benches/proxy_latency.rs -- Criterion benchmarks:**

    Set up the bench harness per Cargo.toml `[[bench]]` config.

    **Benchmark 1: `bench_proxy_latency_p99` (KERN-07)**
    - Start proxy with test CA and mock vendor on allowlist
    - Mock vendor returns immediate 200 with small JSON body
    - Measure: time from sending request through proxy to receiving first response byte
    - Compare with: time for direct request to mock vendor (without proxy)
    - The DIFFERENCE is the proxy overhead
    - Criterion group: iterate over varying concurrency levels (1, 10, 50)
    - Target: overhead <10ms p99, ideal <5ms
    - This benchmark measures CONNECT handshake + TLS interception + relay overhead

    **Benchmark 2: `bench_proxy_throughput` (KERN-08)**
    - Start proxy with mock vendor returning instant responses
    - Fire requests as fast as possible for a fixed duration
    - Measure: requests completed per second
    - Criterion group: iterate over connection counts (1, 2, 4 connections)
    - Target: >10,000 RPS
    - Note: this benchmark may be limited by the mock server rather than the proxy. Use multiple mock servers or a high-performance mock if needed.

    **Benchmark 3: `bench_proxy_memory_steady_state` (KERN-09)**
    - Start proxy
    - Send 10,000 requests with streaming responses (1KB each)
    - Measure: RSS (Resident Set Size) after all requests complete
    - Use `jemalloc_ctl::stats::allocated::read()` for jemalloc-specific memory stats
    - Target: <128MB
    - Note: This is more of a test than a benchmark. Could also be a regular test with assertions.

    **Benchmark implementation notes:**
    - Use `criterion::Criterion` with `criterion::BenchmarkGroup`
    - Use `criterion::async_executor::TokioRuntime` for async benchmarks (criterion 0.5 with async_tokio feature)
    - The test proxy setup (starting server, CA generation) should happen in benchmark setup, not during measurement
    - Use `b.iter(|| async { ... })` for the measured operation

    **Important:** These benchmarks measure the proxy infrastructure, not real AI vendor latency. The mock vendor returns instantly. The overhead we're measuring is purely proxy processing time: CONNECT handling, TLS interception, byte relay. This gives us a clean signal for KERN-07.

    **Add to Cargo.toml if not already present:**
