    Implement the CONNECT tunnel handler that performs TLS interception and the zero-copy bidirectional relay.

    **crates/kernel/src/proxy/connect.rs:**

    **`pub async fn handle_connect(req, cert_cache, pool) -> Result<Response<BoxBody>, ProxyError>`:**
    Follow the exact pattern from research Pattern 1, with these steps:

    1. Extract host from `req.uri().authority()` -- return `ProxyError::MissingAuthority` if missing. Extract both host (domain) and port (default 443).
    2. The allowlist check is ALREADY handled by the AllowlistLayer middleware before this function is called. Do NOT re-check here.
    3. Return HTTP 200 to the client to complete the CONNECT handshake.
    4. Spawn a tokio task for the tunnel:
       a. `hyper::upgrade::on(req).await` to get the upgraded client stream
       b. Get the domain-specific TLS server config from `cert_cache.get_or_create(&host)`
       c. Create a `tokio_rustls::TlsAcceptor` from the server config
       d. Accept TLS from the client: `tls_acceptor.accept(TokioIo::new(upgraded)).await` -- this makes the client think it's talking to the vendor
       e. Now the proxy has cleartext from the client. In Phase 1, we relay bytes directly to upstream. In later phases, this is where inspection happens.
       f. Establish TLS connection to the actual upstream vendor using rustls ClientConfig with webpki roots
       g. Relay bytes bidirectionally between decrypted client stream and encrypted upstream connection

    **Connection to upstream vendor (within the spawned task):**
    - For Phase 1, use `tokio_rustls::TlsConnector` to establish a direct TLS connection to the vendor at `host:port`
    - The custom connection pool (Task 2) will be integrated, but the basic flow should work with direct connections first. Include a `pool.get_or_connect(host, port)` call that the pool module will provide.
    - Apply connect_timeout_ms from config on the upstream TCP connection
    - Apply first_byte_timeout_ms and stream_timeout_ms as appropriate

    **Timeout handling:**
    - Use `tokio::time::timeout()` wrapping the connect, TLS handshake, and stream phases
    - Connect timeout: config.proxy.connect_timeout_ms (default 10s)
    - Stream timeout: config.proxy.stream_timeout_ms (default 5min) -- generous for AI workloads per CONTEXT.md
    - On timeout: return vendor_unreachable_response (for connect) or close with error (for stream)

    **Error handling in the spawned task:**
    - If TLS handshake with client fails: log error, close connection
    - If upstream connection fails: attempt to send an error back through the TLS connection to the client before closing
    - All errors logged with request_id, vendor, and error detail via tracing

    **`ProxyService` struct** (in connect.rs or proxy/mod.rs):
    - Holds `Arc<CertCache>`, `Arc<ConnectionPool>`, `Arc<Config>` (or relevant config subset)
    - Implements `tower::Service<Request<Incoming>>`:
      - Method detection: if `req.method() == Method::CONNECT` -> `handle_connect()`
      - Non-CONNECT requests: return 400 Bad Request (this is an explicit forward proxy, only CONNECT is valid per CONTEXT.md: "HTTPS CONNECT only -- no plaintext HTTP forwarding")
    - Implement Clone for Tower service stack

    **crates/kernel/src/proxy/relay.rs:**

    **`pub async fn bidirectional<C, U>(client, upstream) -> Result<(u64, u64), io::Error>`:**
    - Generic over `AsyncRead + AsyncWrite + Unpin` for both sides
    - Use `tokio::io::copy_bidirectional(&mut client, &mut upstream)` for zero-copy relay
    - This is the hot path -- NO buffering, NO body collection, NO content inspection (that's Phase 3)
    - Log bytes transferred at debug level on completion
    - On error from either side: log the direction that errored, return the error

    **Error propagation on mid-stream disconnect (per CONTEXT.md decisions):**
    - If upstream disconnects during relay: the client side of copy_bidirectional will see EOF
    - For SSE streams: the client SDK detects the connection drop and can retry (per CONTEXT.md "client SDK should be able to detect and retry")
    - For now (Phase 1), clean EOF propagation via copy_bidirectional is sufficient. Protocol-specific error injection (SSE error events, gRPC UNAVAILABLE status) can be added as a refinement.

    **crates/kernel/src/proxy/mod.rs:**
    - Uncomment and add: `pub mod connect;`, `pub mod relay;`, `pub mod pool;`, `pub mod websocket;`
    - Re-export `ProxyService`

    **crates/kernel/src/main.rs -- Complete the server accept loop:**
    - Build the Tower service stack:
      ```
      ServiceBuilder::new()
        .layer(RequestIdLayer)
        .layer(TraceLayer::new_for_http())
        .layer(AllowlistLayer::new(allowlist))
        .service(ProxyService::new(cert_cache, pool, config))
      ```
    - Bind TCP listener on config.proxy.listen_addr
    - Accept loop:
      ```
      loop {
          let (stream, addr) = listener.accept().await?;
          let svc = service.clone();
          tokio::spawn(async move {
              let io = TokioIo::new(stream);
              auto::Builder::new(TokioExecutor::new())
                  .serve_connection_with_upgrades(io, svc)
                  .await
          });
      }
      ```
    - Use `hyper_util::server::conn::auto::Builder` for HTTP/1.1+HTTP/2 auto-detection on the single port (per CONTEXT.md: single listening port with protocol auto-detection)
    - CRITICAL: Use `.serve_connection_with_upgrades()` (not `.serve_connection()`) to enable HTTP CONNECT upgrade support
    - Use `hyper_util::rt::TokioIo` wrapper for tokio::net::TcpStream
    - Use `hyper_util::rt::TokioExecutor` for the executor

    **Graceful shutdown (basic):**
    - Listen for SIGINT/SIGTERM via `tokio::signal::ctrl_c()`
    - On signal: log "shutting down", stop accepting new connections
    - Use a `tokio::sync::watch` channel (bounded, KERN-13 compliant) to broadcast shutdown signal
    - Wait up to 30 seconds for active connections to drain, then force close (per research Open Question 4)

    **KERN-13 compliance:** Any channel created in this plan MUST be bounded. The shutdown watch channel is inherently bounded (single value). If any mpsc channels are needed for connection pool or request routing, use `channel(N)` with explicit capacity.

  <name>Task 2: Implement custom HTTP/2 connection pool with multiple connections per vendor</name>
  <files>
    crates/kernel/src/proxy/pool.rs

  <action>
    Implement a custom HTTP/2 connection pool that maintains multiple TCP connections per AI vendor to avoid single-connection stream saturation (KERN-12). hyper's built-in pool only opens one HTTP/2 connection per host, which caps at ~100-250 concurrent streams.

    **crates/kernel/src/proxy/pool.rs:**

    **`ConnectionPool` struct:**
    - `connections: DashMap<String, Vec<PooledConnection>>` -- map from vendor domain to vector of pooled connections
    - `max_conns_per_vendor: usize` -- from config (default 4)
    - `max_streams_per_conn: usize` -- from config (default 100)
    - `tls_connector: tokio_rustls::TlsConnector` -- shared TLS connector for upstream connections (using webpki root certs)
    - `connect_timeout: Duration` -- from config

    **`PooledConnection` struct:**
    - `sender: hyper::client::conn::http2::SendRequest<BoxBody>` -- handle to send requests on this HTTP/2 connection
    - `active_streams: Arc<AtomicUsize>` -- track how many concurrent streams are active on this connection
    - Connection health tracking: last_used timestamp, is_closed boolean

    **`ConnectionPool::new(config: &PoolConfig, connect_timeout: Duration) -> Self`:**
    - Create TLS connector using `rustls::ClientConfig` with `webpki_roots::TLS_SERVER_ROOTS` for standard certificate validation of upstream AI vendor TLS
    - Initialize empty DashMap

    **`ConnectionPool::get_or_connect(&self, host: &str, port: u16) -> Result<PooledConnection, ProxyError>`:**
    Follow research Pattern 2 logic:
    1. Look up existing connections for this host in DashMap
    2. Find the least-loaded connection where `active_streams < max_streams_per_conn`
       - Use `.iter().filter(...).min_by_key(...)` pattern
       - Clean up dead connections (where the sender reports closed) during iteration
    3. If a suitable connection exists: increment active_streams, return clone
    4. If all connections are saturated AND `conns.len() < max_conns_per_vendor`:
       - Create a new TCP connection to `host:port` with connect_timeout
       - Perform TLS handshake via tls_connector
       - Perform HTTP/2 handshake via `hyper::client::conn::http2::handshake(TokioExecutor::new(), io)`
       - Spawn the connection driver task (the `conn` future from handshake must be polled)
       - Add to the pool vector
       - Return the new connection
    5. If all connections at max AND pool is full: return `ProxyError::PoolExhausted(host)`

    **Connection lifecycle:**
    - The `hyper::client::conn::http2::handshake()` returns `(SendRequest, Connection)`. The `Connection` future must be spawned as a background task to drive the HTTP/2 connection.
    - When the spawned Connection task completes (connection closed), mark the PooledConnection as dead so it gets cleaned up on next access.
    - Implement `Drop` or a cleanup method on PooledConnection to decrement active_streams when a stream completes.

    **`StreamGuard` struct (RAII pattern for stream tracking):**
    - Holds `Arc<AtomicUsize>` reference to active_streams counter
    - On `Drop`: decrements active_streams by 1
    - This ensures streams are always properly tracked even if the relay task panics
    - `ConnectionPool::get_or_connect` returns the sender AND a StreamGuard

    **`ConnectionPool::pool_stats(&self) -> PoolStats`:**
    - Return connection count, active stream count, per-vendor breakdown
    - For metrics/debugging, logged periodically

    **Unit tests (#[cfg(test)]):**
    - Test: new pool starts empty
    - Test: get_or_connect to a host creates exactly one connection on first call
    - Test: multiple calls to same host reuse the same connection until stream limit
    - Test: when max_streams_per_conn is reached, a new connection is created (up to max_conns_per_vendor)
    - Test: when all connections are full, PoolExhausted error is returned
    - Test: StreamGuard correctly decrements active_streams on drop

    **Note on testing:** The unit tests for connection management may need a mock TCP server. Use `tokio::net::TcpListener` bound to localhost for simple connection creation tests, or structure tests around the pool's internal state management (DashMap operations) without requiring real HTTP/2 handshakes. Full integration testing with actual HTTP/2 is deferred to Plan 01-03.

    **KERN-13 compliance:** The pool uses no channels. DashMap is lock-based, not channel-based. The spawned connection driver tasks are fire-and-forget (no channel needed). If any signaling is needed (e.g., connection closed notification), use `tokio::sync::watch` or `tokio::sync::oneshot` (both bounded).

    Implement WebSocket upgrade detection and bidirectional frame relay using tokio-tungstenite, integrated into the CONNECT tunnel handler.

    **crates/kernel/src/proxy/websocket.rs:**

    **`pub fn is_websocket_upgrade(req: &Request<Incoming>) -> bool`:**
    - Check for WebSocket upgrade indicators:
      - HTTP/1.1: `Connection: Upgrade` header + `Upgrade: websocket` header
      - HTTP/2: Extended CONNECT with `:protocol: websocket` pseudo-header (RFC 8441)
    - This is called on the INNER request (after TLS termination) to detect if the client wants WebSocket

    **`pub async fn relay_websocket<C, U>(client_stream: C, upstream_stream: U) -> Result<(), ProxyError>`:**
    Where C and U implement `AsyncRead + AsyncWrite + Unpin`:
    - Wrap both sides with `tokio_tungstenite::WebSocketStream::from_raw_socket()`
    - Use `futures_util::StreamExt` and `futures_util::SinkExt` for the WebSocket stream/sink traits
    - Relay loop using `tokio::select!`:
      ```
      loop {
          tokio::select! {
              msg = client_ws.next() => {
                  match msg {
                      Some(Ok(msg)) => upstream_ws.send(msg).await?,
                      Some(Err(e)) => { log error; break; }
                      None => break, // client closed
                  }
              }
              msg = upstream_ws.next() => {
                  match msg {
                      Some(Ok(msg)) => client_ws.send(msg).await?,
                      Some(Err(e)) => { log error; break; }
                      None => break, // upstream closed
                  }
              }
          }
      }
      ```
    - Handle WebSocket close frames properly: when one side sends Close, forward it to the other side and then close both
    - Handle Ping/Pong: forward Ping from one side to the other, respond with Pong
    - Log frame counts and bytes transferred at debug level on relay completion

    **Error propagation for WebSocket:**
    - If upstream drops: send WebSocket Close frame with code 1011 (Internal Error) to client before closing (per research Pitfall 6)
    - If client drops: close upstream WebSocket cleanly

    **Integration with connect.rs:**
    - After TLS interception in the CONNECT tunnel, the proxy reads the first HTTP request from the decrypted client stream
    - If the request is a WebSocket upgrade: call `handle_websocket_upgrade()` which:
      1. Forwards the upgrade request to the upstream vendor
      2. If upstream accepts (101 Switching Protocols): relay WebSocket frames bidirectionally
      3. If upstream rejects: forward the rejection response to the client
    - If the request is NOT a WebSocket upgrade: proceed with standard HTTP relay (the existing bidirectional byte relay)

    **Important implementation note on the CONNECT tunnel inner protocol:**
    - After the CONNECT tunnel is established and TLS is terminated, the client sends HTTP requests through the tunnel. In Phase 1, the simplest correct approach is:
      1. For the common case (SSE, gRPC): relay raw bytes bidirectionally via `relay::bidirectional()`. This works because SSE is just HTTP, and gRPC is HTTP/2 frames -- both flow through transparently.
      2. For WebSocket: detect the upgrade in the first request and switch to WebSocket frame relay.
    - The research confirms: "SSE is HTTP with text/event-stream content-type -- relay as raw byte stream (no SSE-specific parsing needed in Phase 1)" and "gRPC over HTTP/2 -- the proxy relays HTTP/2 frames transparently after TLS termination; no gRPC-specific decoding needed"
    - So the actual relay mode is: raw bidirectional bytes for everything, with WebSocket frame-level relay as the exception.
    - Update connect.rs to handle this: after TLS handshake with client, peek at the first bytes. If it looks like a standard HTTP request, set up a hyper HTTP connection on the client side to parse requests. If the first request is a WebSocket upgrade, switch to WebSocket relay. Otherwise, fall through to bidirectional byte relay.
    - Alternatively (simpler and recommended for Phase 1): always use raw bidirectional byte relay (`relay::bidirectional`). WebSocket frames will flow through as raw bytes just fine. WebSocket-specific frame relay is only needed when we want to inspect/modify individual frames (Phase 3+). For Phase 1, raw relay is sufficient for all protocols.
    - **Decision: Use raw bidirectional byte relay for ALL protocols in Phase 1.** Create the WebSocket detection and frame relay infrastructure but keep it available for Phase 3 when content inspection requires frame-level access. In Phase 1, the relay is protocol-agnostic bytes.

    **Unit tests (#[cfg(test)]):**
    - Test: `is_websocket_upgrade` returns true for request with `Connection: Upgrade` + `Upgrade: websocket` headers
    - Test: `is_websocket_upgrade` returns false for normal HTTP request
    - Test: `is_websocket_upgrade` returns false for requests with only one of the two headers

    **KERN-13 compliance:** WebSocket relay uses `tokio::select!` (not channels). No unbounded channels.
