    **src/modules/audit/queries.ts:**
    - `queryAuditTrail(client, filters, cursor?, limit?)`:
      Build parameterized ClickHouse query against `evidence_bundles` table.
      - CRITICAL: Use an explicit column list -- DO NOT use `SELECT *`. Select only: `timestamp, bundle_id, kernel_id, actor_identity, department, vendor, model, prompt_hash, response_hash, policy_action, policy_rules_json, token_count, enforcement_latency_us, chain_hash, previous_hash, sequence_number, signature, signing_key_id, dev_signed, schema_version, event_date`. EXCLUDE `prompt_text` and `response_text` columns to comply with CLAUDE.md Invariant 6 (never expose plaintext prompts/responses through the API layer).
      - ALWAYS include date range filter to prune partitions (per Pitfall 3). If no date range provided, default to last 7 days.
      - Use cursor-based pagination: `(timestamp < cursor_ts OR (timestamp = cursor_ts AND bundle_id < cursor_id))` for stable DESC ordering.
      - Filter on LowCardinality columns (department, vendor, model, policy_action) as primary filters.
      - For actor_identity filter, use string matching (non-LC column -- include date range to limit scan).
      - Use `{param:Type}` ClickHouse parameterized query syntax to prevent injection.
      - Fetch `limit + 1` rows to determine `hasMore`.
      - Return `{ items, nextCursor, hasMore }`.

    - `queryHourlyViolations(client, from, to)`:
      Query `mv_hourly_violations` WHERE `hour >= from AND hour <= to`, ordered by `hour ASC`.
      Returns array of `{ hour, policy_action, violation_count, unique_actors, unique_vendors }`.

    - `queryVendorUsage(client, from, to, vendor?)`:
      Query `mv_vendor_usage` with date range and optional vendor filter, ordered by `hour ASC`.

    - `queryDepartmentSummary(client, from, to, department?)`:
      Query `mv_department_summary` with date range and optional department filter, ordered by `hour ASC`.

    **src/modules/audit/enrichment.ts:**
    - `enrichAuditRecords(db, clickhouseRows)`:
      1. Extract unique actor_identity values, policy rule IDs (from policy_rules_json), and vendor names from the result set.
      2. Batch-query PostgreSQL for user display names (`WHERE email IN (...)` on users table).
      3. Batch-query PostgreSQL for vendor display names (`WHERE name IN (...)` on vendors table).
      4. Batch-query PostgreSQL for policy names (parse policy_rules_json for policy IDs, `WHERE id IN (...)`).
      5. Map enrichments back onto each row, using the raw value as fallback if no PostgreSQL record found.
      6. Cache entity lookups in a simple Map for reuse within the same request (not cross-request).
      - Per Pitfall 7: batch enrichment, NOT N+1 per-row lookups.
